# CLAUDE.md — Система за записване на профилактични прегледи

## Цел на проекта
Уеб приложение, с което служители на фирми-клиенти се записват за профилактичен преглед в медицински център чрез **един общ линк** (подобно на SuperDoc). Всички записвания влизат автоматично в една база. Медицинският център ги управлява от админ панел и ги експортира (Excel/CSV, включително във формат за импорт в JOYSTICK). Директна интеграция с JOYSTICK е **извън обхвата** (няма публично API). Само експорт.

Целта е **нулево ръчно събиране** на данни от имейли, Word или телефон. Системата ще се ползва в реална среда с реални лични данни, затова сигурността, коректността при едновременни записвания и GDPR са с приоритет пред „красиви“ екстри.

## Технологичен стек
- **Next.js 15+ (App Router, TypeScript, strict mode)**, деплой на Vercel
- **Supabase**: Postgres, Auth (само за админи), регион **EU (Frankfurt)**
- **Tailwind CSS + shadcn/ui** за UI
- **Resend** + React Email за имейли (изисква потвърден домейн: SPF/DKIM)
- **Cloudflare Turnstile** срещу ботове/спам във формата
- **Zod** за валидация (споделени схеми клиент/сървър)
- **exceljs** за .xlsx експорт
- **date-fns + date-fns-tz**. Всички времена се пазят като `timestamptz` (UTC) и се показват в `Europe/Sofia`.
- Тестове: **Vitest** (unit) + **Playwright** (e2e за основния поток)

## Език и UI
- Целият потребителски интерфейс е **на български**. Кодът, имената на таблиците и коментарите са на английски.
- Формат на дата: `15.10.2026`. Час: `09:00` (24-часов).
- Mobile-first: повечето служители ще отворят линка от телефон.
- Достъпност: етикети на полетата, фокус, контраст, работи без мишка.

## Модел на данните (Supabase / Postgres)

```
campaigns
  id uuid pk
  slug text unique            -- ползва се в линка /book/[slug]
  title text                  -- напр. "Профилактични прегледи – Медицински център"
  location_address text
  location_note text null     -- напр. "Етаж 2, кабинет 5"
  is_active boolean default true
  booking_closes_hours_before int default 2
  created_at timestamptz

slots
  id uuid pk
  campaign_id uuid fk -> campaigns
  starts_at timestamptz
  duration_min int
  capacity int default 1      -- брой места в този час (напр. 2 лекари паралелно)
  is_blocked boolean default false
  unique (campaign_id, starts_at)

bookings
  id uuid pk
  campaign_id uuid fk
  slot_id uuid fk -> slots
  full_name text not null
  phone text not null
  email text not null
  workplace text null
  notes text null             -- полето "Допълнително"
  status text check in ('confirmed','cancelled') default 'confirmed'
  cancel_token uuid default gen_random_uuid()
  consent_at timestamptz not null
  created_at, updated_at timestamptz
  -- един човек = едно активно записване в кампания:
  unique index (campaign_id, lower(email)) where status = 'confirmed'

admins
  user_id uuid pk fk -> auth.users
  email text

audit_log
  id, booking_id, action ('create','update','cancel','admin_cancel'), actor, payload jsonb, created_at
```

Всички промени по схемата са **SQL миграции** в `supabase/migrations/`. Никога не се правят ръчни промени в dashboard-а.

## Критично: записване без двойни резервации
Записването се прави **само** чрез Postgres функцията `book_slot(...)` (`security definer`), извиквана от server action/route handler:
1. `SELECT ... FROM slots WHERE id = $1 FOR UPDATE` заключва реда на часа.
2. Проверява: кампанията е активна, часът не е блокиран, не е в миналото, не е след крайния срок за записване.
3. Брои `confirmed` записванията за слота и ги сравнява с `capacity`.
4. Ако има място, прави insert в `bookings` и връща booking-а. Ако няма, хвърля разпознаваема грешка (`SLOT_FULL`, `DUPLICATE_EMAIL`, `CLOSED`).

UI-ът показва на български: „Този час току-що беше зает. Моля, изберете друг.“ и презарежда свободните часове.

**Задължителен тест:** 20 паралелни заявки за слот с capacity=1 трябва да дадат точно 1 успешна.

## Сигурност (RLS)
- RLS е **включен на всички таблици**.
- Анонимният потребител **няма** SELECT върху `bookings`. Свободните часове се четат през функцията `get_availability(slug)`, която връща само `slot_id, starts_at, duration_min, available_count`. Тя не връща никакви лични данни.
- Админите (има ред в `admins`) имат пълен достъп.
- `SUPABASE_SERVICE_ROLE_KEY` се ползва само на сървъра и никога не се импортира в client компонент.
- Turnstile токенът се проверява на сървъра преди `book_slot`.
- Rate limit на endpoint-а за записване (напр. по IP, 10/час).
- Валидация със Zod: телефон в BG формат (`08XXXXXXXX` / `+359...`, нормализиран към `+359`), валиден имейл, ограничения на дължината на текстовите полета.

## Публичен поток (служител)
`/book/[slug]`:
1. Заглавие на кампанията и адрес.
2. Избор на дата (само дати със свободни часове).
3. Решетка с часове. Заетите/пълните са видими, но неактивни.
4. Форма: Име и фамилия*, Телефон*, Имейл*, Работно място, Допълнително (textarea), чекбокс за съгласие с обработка на лични данни* (линк към кратка политика), Turnstile.
5. Бутон **„Запази час“**. По време на заявката е disabled, за да няма двойно натискане.
6. Страница за потвърждение: „Вашият профилактичен преглед е записан успешно.“ + дата, час, адрес, бутон „Добави в календар“ (.ics).
7. Имейл за потвърждение със същите данни, .ics прикачен файл и линк за отмяна `/cancel/[token]`.

`/cancel/[token]`: показва записването, бутон „Отмени записването“, освобождава часа и изпраща имейл.

Опционално (Фаза 5): имейл-напомняне 1 ден преди прегледа чрез Vercel Cron.

## Админ панел (`/admin`)
- Вход: Supabase Auth с magic link. Достъп имат само потребители от `admins`. Няма публична регистрация.
- **Кампании:** създаване/редакция, slug, адрес, активна/неактивна, бутон „Копирай линка“.
- **Генератор на часове:** дата(и), начален час, краен час, продължителност, капацитет → преглед → създаване. Отделни часове могат да се блокират/изтриват (изтриване само ако няма записвания).
- **Записвания:** таблица с филтри по кампания, дата и час и търсене по име/телефон/имейл. Редакция на записване, преместване в друг час (пак през заключваща логика), отмяна (с имейл до служителя).
- **Експорт:** `.xlsx` и `.csv` (UTF-8 **с BOM**, разделител `;` за българския Excel) по текущите филтри. Колони: Име и фамилия, Телефон, Имейл, Работно място, Дата, Час, Допълнително, Статус, Записан на.
- **Експорт за JOYSTICK:** отделен бутон „Експорт за JOYSTICK“. Ползва профил с конфигурируемо мапване на колони (име на колона, ред, формат на дата/час/телефон, разделител, кодировка) в `lib/export/profiles.ts`. Точният формат ще бъде даден по примерен импорт файл от JOYSTICK. Дотогава профилът е копие на стандартния. Промяната на формата трябва да е редакция само на профила, без друг код.
- **Мапване на колоните:** името на колоната и името на полето да се пазят отделно (`{ header: "Име и фамилия", field: "full_name", format?: fn }`), за да се добавят лесно нови профили.
- Всяко админ действие се записва в `audit_log`.

## Поддръжка в production
- **Keep-alive:** Vercel Cron веднъж дневно извиква `/api/cron/keepalive` (проста заявка към базата), за да не се приспи безплатният Supabase проект. Endpoint-ът е защитен с `CRON_SECRET`.
- **Бекъп:** GitHub Action веднъж седмично прави `pg_dump` и пази криптиран артефакт.
- **GDPR:** cron веднъж месечно анонимизира записвания по-стари от N месеца (`DATA_RETENTION_MONTHS`, по подразбиране 12). Има страница с политика за поверителност.
- Грешките се логват на сървъра. Личните данни **не** се логват.
- Страници `loading`, `error` и `not-found` на български. Неактивна кампания показва „Записването е затворено“.

## Взети решения (одобрени от собственика, 2026-10-07)
Тези решения допълват и уточняват изискванията по-горе. При конфликт важат те.

**Git**
- Работим в git с малки commit-и. Remote: частно репо `DaniHristov/profilaktika-booking`. **Push само когато собственикът изрично поиска.**

**Права в базата** („Automatically expose new tables“ е изключено в Supabase)
- RLS е включен на всички таблици. `anon` **няма никакви** права върху таблиците (`revoke all`).
- `authenticated` получава изричен `GRANT select, insert, update, delete` върху таблиците, по които работи админът. Реалният достъп се решава от RLS политиките чрез `is_admin()`.
- `admins` и `audit_log` за `authenticated` имат само select (през RLS само за админи). Записи в `audit_log` идват само от `security definer` функции.
- За **всяка** функция: `revoke execute ... from public` (и от `anon`, `authenticated`), после изричен `grant` само където трябва:
  - `get_campaign_public`, `get_availability` → `anon`, `authenticated`
  - `is_admin` → само `authenticated`
  - `book_slot`, `check_rate_limit` и бъдещата функция за отмяна по токен → **само `service_role`**. Вика ги само сървърът (server action / route handler) след Zod валидация, Turnstile и rate limit. Причина: anon ключът е публичен и всяка функция, разрешена за `anon`, може да се извика директно през `/rest/v1/rpc/...`, заобикаляйки защитите.
- pgTAP тест (`supabase/tests/`) проверява, че `anon` не може да изпълни никоя друга функция в `public`.
- Всички `security definer` функции имат `set search_path = ''` и пълни имена (`public.x`).

**Публично четене**
- `get_campaign_public(slug)` → `title, location_address, location_note, is_active`. Анонимният потребител няма SELECT върху `campaigns`.
- `get_availability(slug)` връща само часове на **активна** кампания, които **не са блокирани** и започват след `now() + booking_closes_hours_before`. Пълните часове се връщат с `available_count = 0` (UI ги показва неактивни). Блокираните и минали часове не се връщат. Неактивна кампания → празен списък.

**Модел на данните**
- `audit_log`: `actor text` (`'public'` или `admin:<user_id>`), `booking_id` nullable с `on delete set null`, `action` с check constraint. `payload` може да съдържа лични данни, затова GDPR анонимизацията (Фаза 5) чисти и него.
- Ограничения на дължината (DB check + Zod): име 100, телефон 20, имейл 254, работно място 150, допълнително 1000 знака.
- Изтриване: `on delete restrict` навсякъде. Кампания или час със записвания не може да се изтрие. Записванията никога не се трият, само се отменят или анонимизират.
- `bookings` сочи към слота с композитен FK `(slot_id, campaign_id)`, така че часът винаги е от същата кампания.
- Без `citext`, ползва се `lower(email)`.

**Админи**
- Първият админ се добавя ръчно с документирана SQL команда (insert в `admins` след първия magic link вход). Без автоматична регистрация.

**Телефон (Фаза 2)**
- Приемат се мобилни и стационарни BG номера, плюс международни, започващи с `+`. Валидация с **libphonenumber-js** (регион по подразбиране `BG`). Записва се в **E.164** (напр. `+359888123456`).

**Нормализиране (преди запис)**
- Имейл: `trim` + малки букви. Име: `trim` + единични интервали. Телефон: E.164 (по-горе). Работно място и „Допълнително“: `trim`, празен низ → `null`.

**Rate limit на записването**
- IP: на Vercel **само** `x-real-ip`. Никога първата стойност от `x-forwarded-for` (клиентът може да я подправи). Локално fallback към `127.0.0.1`.
- IP-то не се пази в чист вид: HMAC-SHA256 с `IP_HASH_SECRET`. Редовете се трият след 24 часа.
- Лимити по IP: **20 опита за 10 минути** и **30 успешни записвания за час** (служителите на една фирма често са зад общ IP, затова не 10/час).

**Текстове на грешките (публичен поток)**
- `SLOT_FULL`: „Този час току-що беше зает. Моля, изберете друг.“ (+ презареждане на часовете, попълнените данни остават)
- `DUPLICATE_EMAIL`: „С този имейл вече има записан час за тази кампания. Ако искате да го смените, първо отменете записването от линка в имейла за потвърждение.“
- `CLOSED`: „Записването за този час вече е затворено. Моля, изберете друг.“
- Rate limit: „Твърде много опити. Моля, опитайте отново след малко.“

**Публична страница**
- Потвърждението се показва на същата страница (без redirect и без токен в URL). „Добави в календар“ генерира .ics в браузъра без лични данни. Имейлът (Фаза 3) е трайното потвърждение.
- Часовете се показват като свободни/заети, без брой места.
- Свободните часове не се кешират.
- Turnstile: локално официалните тестови ключове на Cloudflare. Истинският widget се създава след деплой във Vercel (hostname). Тестовият secret се отказва в production.
- `/privacy`: временен текст с плейсхолдъри, докато клиентът не даде данните на администратора.

**Дати**
- Фаза 2 ползва `Intl.DateTimeFormat` с `Europe/Sofia`. date-fns / date-fns-tz се отлагат за Фаза 4 (генератор на часове).

**Тестове**
- `npm test`: unit. `npm run test:integration`: срещу локалния Supabase (вкл. 20 паралелни заявки). `npm run test:db`: pgTAP. Всички се пускат в края на всяка фаза.

**Seed**
- Тестова кампания „Профилактични прегледи – Медицински център“, часове 09:00–12:00 през 30 мин (последният започва 11:30), капацитет 1, за **следващите 2 работни дни** спрямо момента на `supabase db reset` (`Europe/Sofia`), за да не остаряват.

**Next.js**
- Сесийният middleware се казва `proxy.ts` (Next 16+) или `middleware.ts` (Next 15), според инсталираната версия.

Оригиналните изисквания на клиента са в `docs/client-requirements.md`.
